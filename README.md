# Nykaa Domain Support Agent

**Track: E-commerce**

A deterministic, educational e-commerce customer-support agent built with **LangGraph**, **ChromaDB**, **FastAPI**, **MCP**, and **SQLite checkpointing**.

> This is an educational project. All policies and order data are synthetic and do not represent Nykaa's real policies.

---

## 1. Project Overview

This project implements a domain-specific support agent for an e-commerce platform.

The agent can:

- Answer policy and FAQ questions from a local knowledge base.
- Look up order status from a synthetic order dataset.
- Calculate an escalation score for order-related issues.
- Route questions using a LangGraph workflow.
- Maintain persisted conversation history.
- Produce validated structured JSON responses.
- Detect and mask selected PII.
- Detect prompt-injection attempts.
- Refuse unsupported and out-of-scope questions.
- Expose the agent through FastAPI.
- Produce structured JSONL request logs.
- Evaluate retrieval and RAG quality.
- Demonstrate a real MCP client/server round trip.
- Demonstrate SQLite-based LangGraph checkpointing.
- Demonstrate retry and timeout handling.

The default graded mode uses a deterministic mock LLM and does not require API keys or external network access.

## 4. RAG Pipeline

The RAG pipeline uses:

- Sentence-transformer embeddings: `all-MiniLM-L6-v2`
- ChromaDB vector store
- Semantic similarity retrieval
- Top-3 document retrieval
- A calibrated similarity-distance threshold
- Grounded response generation

The main retrieval modules are:

- `src/chunking.py`
- `src/vector_store.py`
- `src/retrieval.py`
- `src/evaluation.py`

## 5. Chunking Strategies

Two different chunking strategies were implemented and evaluated.

### Strategy 1: Fixed-size chunking

The fixed-size strategy creates chunks using a fixed-size window with overlap.

Result: **30 chunks**

### Strategy 2: Sentence / structure-aware chunking

The second strategy preserves document structure such as headings, paragraphs and table-like content while creating smaller semantic chunks.

Result: **124 chunks**

Both strategies use separate ChromaDB collections so they can be evaluated independently.

## 6. Retrieval Evaluation

Retrieval was evaluated using:

- Precision@3
- Recall@3

The evaluation contains in-scope support queries covering multiple policy topics and out-of-scope queries.

### Results

| Strategy | Precision@3 | Recall@3 |
|---|---:|---:|
| Fixed-size | 0.73 | 1.00 |
| Sentence / structure-aware | **0.80** | **1.00** |

The sentence / structure-aware strategy was selected because it achieved higher Precision@3 while maintaining the same Recall@3.

## 7. Grounded Generation Calibration

The support agent only generates a policy answer when relevant retrieved context passes the groundedness check.

A threshold calibration experiment was performed using:

- 5 in-scope queries
- 5 out-of-scope queries
- Top-1 retrieval distance
- Candidate thresholds from 0.70 to 1.30

### Observed top-1 distances

#### In-scope queries

    0.6256
    0.2745
    0.6712
    0.7884
    0.8984

#### Out-of-scope queries

    1.6990
    1.7912
    1.8312
    1.8859
    1.7333

The observed clusters showed a clear separation between relevant and out-of-scope retrievals.

### Selected threshold

**0.90**

The selected threshold achieved:

**Balanced Accuracy = 1.00**

At runtime, unsupported queries such as weather, general knowledge, or unrelated questions are refused instead of being answered from unrelated retrieved documents.

## 9. Escalation Score

The escalation score is deliberately designed as a normalized value between **0 and 1**.

### Formula

    escalation_score =
        0.6 × delayed_signal
        + 0.4 × normalized_recency

where:

    delayed_signal =
        1 if delayed_shipment == "Yes"
        0 otherwise

and:

    normalized_recency =
        days_since_created / 30

The recency component is clipped to the `[0, 1]` range.

Therefore:

    0 ≤ escalation_score ≤ 1

### Escalation levels

| Score | Level |
|---:|---:|
| < 0.60 | Level 1 |
| 0.60–0.79 | Level 2 |
| ≥ 0.80 | Level 3 |

The design gives more weight to an explicit delayed-shipment signal while still increasing urgency for older orders.

## 10. LangGraph Agent

The main agent is implemented in:

`src/agent.py`

The workflow contains multiple LangGraph nodes, including:

    Input Guardrail
          ↓
    Intent Router
          ↓
    Order Status / Retrieval
          ↓
    Groundedness Check
          ↓
    Response Generation
          ↓
    Escalation
          ↓
    Structured Output

The graph contains more than the required four nodes and includes conditional routing.

### Main routing behaviour

Policy questions are routed to the knowledge-base retrieval path.

Order-related questions containing an order ID or order-status intent are routed to the order lookup path.

Unsupported or unsafe input is handled by guardrails.

---

## 11. Conversation Memory

Conversation history is persisted as JSON.

The memory workflow supports:

- Multi-turn conversation history
- Continuing an existing conversation
- Starting a fresh conversation with a separate history

This allows the agent to preserve relevant context between turns while still supporting a clean reset.

## 12. Structured Output

Agent responses are validated using a Pydantic schema.

The response contains structured fields including:

    answer
    intent
    grounded
    blocked
    sources
    escalation_score
    escalation_level

The escalation score is constrained to:

    0 ≤ escalation_score ≤ 1

Every final response passes through structured validation before being returned.

---

## 13. Guardrails

Two input-side protections are implemented.

### PII masking

The agent masks:

- Indian phone-number patterns
- Card last-four information

Examples are represented as:

    [PHONE_REDACTED]
    [CARD_LAST4_REDACTED]

### Prompt injection protection

Common prompt-injection patterns are detected and blocked before normal processing.

### Output groundedness

If the retrieval stage cannot provide sufficiently relevant policy context, the agent does not invent an answer.

Instead, it returns a safe fallback response.

## 18. SQLite Checkpointing

SQLite checkpointing is demonstrated in:

`src/checkpoint_demo.py`

The checkpoint database is:

`logs/checkpoints.sqlite`

The demo uses the fixed LangGraph thread:

`nykaa-interrupt-demo-002`

The workflow is interrupted before completion and then resumed using the saved checkpoint.

The demonstration shows that previously completed work is not re-executed when the same thread resumes.

---

## 19. Retry Demonstration

Retry behaviour is demonstrated in:

`src/retry_demo.py`

The demo simulates a transient service failure.

The operation fails on the first two attempts and succeeds on the third attempt.

The current demonstration uses:

- Maximum attempts: **3**
- Retry interval: **0.5 seconds**

The successful recovery demonstrates that transient failure does not necessarily terminate the workflow.

---

## 20. Timeout Demonstration

Timeout behaviour is demonstrated in:

`src/timeout_demo.py`

Two scenarios are demonstrated.

### Per-node timeout

A slow node exceeds its configured timeout.

### Global workflow timeout

The complete workflow exceeds its configured global timeout.

The demo records elapsed execution time and reports the corresponding timeout condition.

> Note: the current demonstration focuses on timeout detection/reporting rather than hard process-level cancellation.
